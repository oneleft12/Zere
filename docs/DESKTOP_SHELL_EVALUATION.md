# Этап 6: Решение по десктопу — оценка вариантов

## Статус: ОЦЕНКА ВЫПОЛНЕНА (этап 6 ✅)

Решение о **выборе конкретного варианта** принимается по факту использования
панели (после этапов 1–5 — они завершены). Документ фиксирует варианты,
стоимость, критерии выбора и рекомендацию.

## Контекст

Что уже есть и не меняется:

- **SPA-панель** (11 экранов, Vite + vanilla TS) — работает в браузере,
  раздаётся `PanelServer`/`jarvis.api.server` по `127.0.0.1` с токеном;
- **один API-контракт** (`docs/api/openapi.yaml`) на две реализации
  (C# и Python) — десктоп-оболочка обязана работать поверх того же API;
- продукт — **Windows-first** (.NET 10, `UseWindowsForms=true` уже подключён);
- консоль уже умеет открывать панель в браузере (команда `панель`/`panel`).

Потребность этапа 6: иконка в трее, окно «всегда под рукой», минимум новых
зависимостей, без дублирования UI и без ослабления защиты loopback+токен.

## Варианты

### A. Только трей (без окна) — WinForms `NotifyIcon`
Иконка в трее: меню «Открыть панель» (браузер), «Показать статус», выход.
Панель остаётся в браузере — UI не переписывается вообще.

- **Стоимость:** ~0.5–1 день, нулевые новые зависимости (WinForms уже
  подключён), тривиально для обеих реализаций (CLI иконку не требует).
- **Минус:** нет автономного окна.

### B. WPF/WinForms-окно + WebView2 поверх существующей SPA — **рекомендуемый кандидат**
Оболочка: одно окно с контролом WebView2, навигация на
`http://127.0.0.1:<port>` (токен панель читает сама из `<meta>`), иконка в
трее, сворачивание вместо закрытия, единственный экземпляр.

- **Стоимость:** ~2–4 дня. UI панели **не переписывается** — паритет экранов,
  тем и i18n достаётся даром; контракт один, тесты те же.
- **Зависимость:** WebView2 Runtime — предустановлен в Windows 11 и с Edge в
  Windows 10 (Evergreen); в редком случае — бутстрапер.
- **Минусы:** тонкая прослойка (окно/трей) — вторая точка входа рядом с
  консолью (нужен single-instance и общий признак «сервер уже запущен»);
  тёмная тема WebView2 следует за системной, панель свою не теряет.
- **Прецедент:** аналогичные хабы на WPF + WebView2 без Electron
  (например, [webviewhub](https://github.com/YuriiHaidur/webviewhub));
  официальный гайд — [Getting started with WebView2 in WPF](https://learn.microsoft.com/en-us/microsoft-edge/webview2/get-started/wpf).

### C. Нативный WPF-клиент (переписать 11 экранов)
Полностью нативный UI поверх того же API.

- **Стоимость:** ~3–4 недели + **постоянный паритет**: каждый экран, тема,
  i18n и компонентная система живут в двух кодовых базах — ровно тот
  README/AGENTS-дрейф, который план считает риском №1.
- **Оправдано**, только если браузерная панель покажет системные проблемы
  (производительность, нативные API окна). Пока не показала.

### D. Avalonia (кроссплатформная перепись)
[Avalonia](https://docs.avaloniaui.net/) (11.3.x / 12.1.x) даёт трей
([TrayIcon](https://docs.avaloniaui.net/api/avalonia/controls/trayicon)) и
Skia-рендер, но это **новый стек** (XAML-диалект, свой hot-reload, свой
пайплайн) плюс перепись всех экранов — те же ~3–4 недели, что и C, при том
что продукт Windows-only и кроссплатформенность не востребована (Python-порт
— серверный, GUI не нужен на Linux/macOS). К тому же WebView2 в Avalonia —
через сторонний плагин.

### E. Tauri / Electron — отклоняется
Сторонний рантайм (Rust-тулчейн у Tauri, ~100 МБ Chromium у Electron),
дублирование логики аутентификации и контракта вне .NET-решения, третий
язык в стеке. Для локального приложения с уже готовой SPA — чистые издержки.

## Сравнение

| Вариант | Стоимость | UI-паритет | Новые зависимости | Риск |
|---|---|---|---|---|
| A. Трей без окна | 0.5–1 дн | нет переписи | нет | минимальный |
| **B. WebView2-оболочка** | **2–4 дн** | **100% (та же SPA)** | WebView2 Runtime (в системе) | низкий |
| C. Нативный WPF | 3–4 нед + поддержка | дублирование | нет | дрейф UI |
| D. Avalonia | 3–4 нед + новый стек | дублирование | Avalonia | дрейф + стек |
| E. Tauri/Electron | 2–3 нед | дублирование | рантайм/тулчейн | контракт вне .NET |

## Критерии решения (по факту использования панели)

1. Панель в браузере устраивает → **ничего не делаем** (трей не нужен).
2. Нужен быстрый доступ «одним кликом» → **вариант A** (трей, 1 день).
3. Нужно автономное окно «как приложение» → **вариант B** (WebView2).
4. Пункты C/D — только по факту системных проблем браузерного UI
   (по данным использования: FPS, память, нативные требования);
   E — не рассматриваем.

## Рекомендация

**Готовая дорожка: A → B.** Оба варианта сохраняют один API, один UI и нулевой
дрейф; C/D — только с измеримым поводом, E — отклонён. Дорожка не начинается
до первого сигнала использования (план: «решение принимается по факту
использования панели»); когда сигнал придёт, оценка уже готова и менять
больше нечего.
