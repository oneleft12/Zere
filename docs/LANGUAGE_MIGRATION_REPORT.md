# Отчёт: оценка перехода JARVIS на другой язык

**Дата:** 2026
**Объект:** JARVIS — персональный AI-ассистент для Windows, C# / .NET 10
**Контекст:** у ИИ (модели, генерирующей код) сильный фокус обучения на Python; знание C# — результат переноса знаний, а не нативного обучения. Интересно: развязывает ли это руки, что с производительностью и масштабируемостью.

---

## 1. Текущее состояние проекта (факт по коду)

| Параметр | Значение |
|---|---|
| Файлов `.cs` (без backups) | 109 |
| Строк кода (без backups) | ~8 300 |
| Проектов в решении | 6 (`App`, `Core`, `AI`, `Memory`, `Tools`, `Voice`) |
| Целевая платформа | `net10.0-windows7.0` (жёсткая привязка к Windows) |
| Внешние NuGet-зависимости | `Microsoft.Data.Sqlite`, `NAudio`, `Whisper.net`, `System.Management`, `Microsoft.Extensions.DependencyInjection` |
| Windows-специфика | P/Invoke (объём, питание), `Microsoft.Win32` (реестр), WMI, WinForms/Drawing |
| Внешние процессы | Ollama (HTTP), Piper (exe) |

Ключевой вывод из осмотра: **узкие места проекта не в C#-коде, а во внешних вызовах** — инференс LLM в Ollama, STT в Whisper-рантайме, TTS в процессе Piper. Сам конвейер (парсинг команд, маршрутизация хендлеров, SQLite, HTTP) — лёгкая CPU-нагрузка.

---

## 2. Кандидаты на миграцию

### Вариант A. Python (основной кандидат)

**За:**
- **Нативное соответствие фокусу обучения ИИ на Python.** Код, который ИИ генерирует на Python, будет качественнее, а не «переносом знаний с C#». Это прямой выигрыш в скорости разработки, т.к. почти вся эволюция JARVIS — это генерация/доработка кода ИИ.
- **Экосистема AI — лучшая в мире:** `faster-whisper` (STT быстрее и легче текущего `Whisper.net`), `piper-tts` (официальный Python-API вместо запуска exe), `openai`/`ollama` клиенты из коробки, `langchain`, `llama-index`, RAG-библиотеки, `sentence-transformers` для эмбеддингов памяти. Граница «просто LLM-клиент» → «агент с инструментами, памятью, эмбеддингами» в Python проходит куда проще.
- **Web-панель** (`docs/WEB_PANEL_PLAN.md`) — `FastAPI`/`uvicorn` вместо отдельного ASP.NET слоя. Одна экосистема.
- **Голос:** `pycaw` (громкость), `sounddevice`/`pyaudio` (запись), `comtypes` (CoreAudio) — всё зрелое. Реестр — `winreg` из стандартной библиотеки. WMI — `wmi`/`pywin32`.
- **Плагины:** перезагружаемые Python-модули через `importlib` проще, чем работающий поверх `Assembly.LoadFrom` (сейчас в `PluginManager` уже есть костыль с выгрузкой DLL из-за блокировки файла).
- **Развязывает руки:** меньше ритуала (csproj/slnx/restore/build), быстрее прототипы, REPL для отладки, больше готовых решений «из коробки».

**Против:**
- **Производительность самого языка** — Python в 30–100× медленнее C# на CPU-коде. Но: конвейер JARVIS — это I/O-нагрузка (HTTP к Ollama, subprocess к Piper, SQLite), реальный CPU-код — пребывание аудио и парсинг — тривиален. **На пользовательском латентном времени переход не заметен.**
- **GIL** — мешает только чистым CPU-потокам; решается `asyncio` (весь I/O) и `multiprocessing`/выносом в нативные библиотеки (Whisper, ONNX уже там).
- **Упаковка под Windows:** `PyInstaller`/`uv` дают единый дистрибутив, но он крупнее и капризнее, чем self-contained .NET. Риск «не запустилось у пользователя» выше.
- **Типобезопасность:** `Nullable`-аннотации C# ловят ошибки на компиляции; Python — только `mypy`/`pyright` на CI, и то частично.
- **P/Invoke-тонкости** (объём через CoreAudio COM, захват экрана) придётся переписывать на `pycaw`/`comtypes`/`mss` — зрелые, но это не «конвертация», а ручной рерайт ~5–7 файлов.
- Плагины `.dll` (если они у внешних авторов) станут несовместимы — только Python-плагины.

### Вариант B. Rust

- **Производительность:** лучшая из всех вариантов, включая C# на отдельных задачах; отличный FFI.
- **Но:** медленная разработка, крутая кривая обучения, ИИ-фокус на Rust слабее, чем на Python/C#. Для ассистента, где 95% времени — ожидание LLM, выигрыш нулевой. **Не рекомендуется.**

### Вариант C. Go

- Простая сборка, хороший конкурентный I/O, но: слабая Windows-специфика (реестр, CoreAudio, WMI — наполовину готовые библиотеки), слабая AI-экосистема. **Не рекомендуется.**

### Вариант D. Остаться на C#

- .NET 10 — отличный, быстрый, типобезопасный, Windows-first. Проблема только одна, но она системная: **ИИ-модель генерирует C# заметно менее уверенно, чем Python.** Поскольку JARVIS развивается силами ИИ, это постоянное трение в каждой задаче.

## 3. Оценка по подсистемам

| Подсистема | Сложность перехода на Python | Комментарий |
|---|---|---|
| `JARVIS.AI` (Ollama HTTP, 144 стр.) | 🟢 Низкая | `httpx`/`ollama` — 1:1, даже короче |
| `JARVIS.Memory` (SQLite) | 🟢 Низкая | `sqlite3` из stdlib / `aiosqlite`; схема переносится как есть |
| `JARVIS.Core` (engine, pipeline, DI, plugins) | 🟡 Средняя | DI → простая фабрика или `dependency-injector`; плагины DLL → `importlib`; логика та же |
| `JARVIS.Tools/Applications` (реестр, сканеры) | 🟡 Средняя | `winreg` + `pathlib` — прямой аналог, рерайт ~10 файлов |
| `JARVIS.Tools` Windows (громкость, процессы, экран) | 🟠 Средне-высокая | `pycaw`, `psutil`, `mss`, `comtypes` — зрелое, но P/Invoke-код переписывается вручную |
| `JARVIS.Voice` (Whisper/Piper/NAudio) | 🟢 Низкая (даже выигрыш) | `faster-whisper` + `sounddevice` + `piper` Python-API; выпадает ручной запуск exe |
| Web-панель (план) | 🟢 Низкая (выигрыш) | `FastAPI` — быстрее, чем писать ASP.NET |

## 4. Ответы на поставленные вопросы

### Развяжет ли Python руки?
**Да, в основном за счёт экосистемы и скорости итерации, а не языка.** Конкретно:
1. AI/RAG-фичи (эмбеддинги в память, агентные циклы, tool-calling фреймворки) в Python имеют готовые библиотеки; в C# их меньше и они менее свежие.
2. ИИ генерирует Python качественнее → каждая следующая задача дешевле.
3. Web-панель, скрипты, автоматизация — одна экосистема вместо двух.
4. REPL и hot-reload ускоряют отладку голосового конвейера.

### Производительность?
**Для JARVIS — практически не изменится.** Время ответа складывается из: инференса Ollama (вне процесса, не зависит от языка) + STT/TTS (нативные рантаймы: ggml/ONNX/процесс Piper) + лёгкий конвейер (миллисекунды в обоих вариантах). Python-цикл добавит единицы–десятки мс на команду. Если когда-нибудь понадобится тяжёлый CPU-код (например, собственный RAG/векторный поиск) — он всё равно уйдёт в нативные расширения (`numpy`, `onnxruntime`), где GIL не участвует.

### Масштабируемость?
**Архитектурная масштабируемость одинаковая** (6 модулей, pipeline, плагины — переносятся 1:1). Операционная: Python проще горизонтально масштабировать как **сервис** (FastAPI + `asyncio`, деплой на любой ОС, Docker), если JARVIS вырастет из консольного приложения в сетевой агент. Вертикально (скорость на одном ядере) — выигрывает C#, но, как отмечено выше, это не бутылочное горлышко проекта.

## 5. Оценка трудозатрат

| Этап | Объём |
|---|---|
| AI + Memory + Core-pipeline (перенос логики) | ~2–4 дня |
| Tools (реестр, процессы, громкость, файлы, игры) | ~3–5 дней |
| Voice (faster-whisper, piper, запись/воспроизведение) | ~2–3 дня |
| Плагины + конфигурация + DI | ~1–2 дня |
| Сквозное тестирование на Windows, упаковка | ~2–3 дня |
| **Итого** | **~2–3 недели** при размере ~8.3k строк |

(Проект компактный; оценка консервативная, с учётом ручного рерайта Windows-специфики.)

## 6. Рекомендация

**Переход на Python для JARVIS — оправдан, если приоритет — скорость развития и AI-фичи** (что полностью совпадает с природой проекта). Производительность и масштабируемость не пострадают, узкие места и так во внешних нативных рантаймах.

Практические варианты по приоритету:

1. **Рекомендуется: полная миграция на Python** — при готовности выделить ~2–3 недели. Максимум выигрыша от фокуса ИИ на Python и экосистемы AI; риски ограничены упаковкой под Windows и рерайтом 5–7 Windows-специфичных файлов.
2. **Компромисс: гибрид** — оставить C# `Tools`/`Voice` как есть, переписать на Python `Core`+`AI`+`Memory` и звать C#-часть как subprocess/CLI. Минимум риска, но постоянный мост между мирами — технический долг.
3. **Безопасно: остаться на C#** — если стабильность текущей базы важнее, чем скорость новых фич; можно сгладить трение ИИ с C# строгими правилами в AGENTS.md (стиль, паттерны, примеры).

Переход на Rust/Go для данного проекта **не рекомендуется** — выигрыш в производительности не нужен, а экосистема AI и удобство работы ИИ с языком хуже, чем у Python.
