# Отчёт: анализ проекта ZERE

**Дата:** 2026-10-21
**Ветка:** `python-port` (HEAD `04381dd`, «Конспектор: материал превращается в конспект в Obsidian»)
**Область:** весь трек-код репозитория — Python-пакет `zere/` + `main.py`, C#-решение (6 проектов, .NET 10), панель `panel/`, тесты, установщик, документация.
**Метод:** полное чтение структуры и ключевых модулей, прогон тестов, статические проверки (ссылки на модули и классы, дубликаты, маршруты, секреты), анализ git-истории и рабочей копии.

Отличие от прошлых отчётов (`PROJECT_AUDIT_REPORT.md` 2026-09-23, `PROJECT_ANALYSIS_2026-10-05.md`): здесь проверялось **текущее состояние исполнением** и отдельно — то, что за прошедшие две недели появились две новые крупные подсистемы (конспектор, MCP-плагины) и что они попали в репозиторий иначе, чем предыдущий код.

## 1. Резюме

Проект зрелый: слоистая архитектура выдержана, контракт панели синхронизирован с OpenAPI, безопасность локального сервера продумана, тестов стало 730 и они проходят полностью. Прежние P0/P1 (несохраняемая история, path traversal, подтверждения без срока, недостижимый «найди файл», несоединённые плагины, отсутствие CI) закрыты — проверено по коду.

Главные проблемы сейчас не в качестве отдельного модуля, а в **процессе**:

1. **Две полноценные реализации одного продукта** (~50 000 строк кода) продолжают развиваться параллельно, разошлись по составу функций, и репозиторий не фиксирует, какая из них ведущая.
2. **CI прогоняет 63 % тестов**, а тесты двух самых новых подсистем не прогоняются вообще; более того, запуск их привычным для репозитория способом даёт «зелёный» результат при нуле выполненных тестов.
3. **~1 300 строк мёртвого кода** в обеих реализациях (портирован 1:1, но нигде не подключён) и гигиена репозитория (85 МБ медиа в корне, посторонний `site-avtosalon/`, нет LICENSE, changelog остановился на v1.1 при версии 1.8.0).

## 4. Архитектура: что устроено хорошо

- **Слойность и паттерны выдержаны:** `App → Core → AI/Memory/Tools/Voice`, конвейер обработчиков с `can_handle/handle`, роутеры команд (`*CommandRouter` + `*CommandType`), репозитории SQLite, свой мини-DI-контейнер (`zere/core/services.py`), плагины (`IPlugin`/`IPersonalityPlugin`/`ICommandHandlerPlugin`).
- **Контракт панели как первый класс:** `docs/api/openapi.yaml` (2 741 строка) описывает все 32 маршрута Python-сервера; в CI есть контрактные тесты и отдельный прогон против **живой C#-панели** на фейковом OpenAI-провайдере (`tests/fake_openai_server.py`) — без сети и без настоящих ключей.
- **Безопасность локального сервера:** только `127.0.0.1`, проверка `Host` (защита от DNS-rebinding), `X-ZERE-Token` со сравнением через `hmac.compare_digest`, одноразовые челленджи на kill/power (`consume_challenge`, TTL), токен 32 байта в `config/panel.token` с сужением прав через `icacls` (`zere/core/security/file_access.py`).
- **Идемпотентность данных:** параметризованный SQL, совместимость со старым `jarvis.db` (`tests/test_db_compat.py`), атомарная запись заметок конспектора.
- **Дисциплина тестов:** высокая плотность проверок (2.5–6 `assert` на тест), фейковые HTTP/MCP/спикер вместо сети и устройств, изоляция журнала в tmp (`tests/conftest.py`).
- **`scripts/check_port.py`** — AST-контракт: каждый `from zere.X import Y` проверяется на существование модуля и символа. Дешёвый и эффективный барьер для порта.
- **Продуманные фолбэки:** GigaAM → Whisper, KWS → прежний wake word, ChatTTS/Silero → текстовый режим, C#-спикер → Python-вывод звука.

## 5. Находки

### 5.1 Главный стратегический риск: две реализации, и не сказано, какая ведущая

Python-порт и C#-решение — не «код и архив», а две живые кодовые базы:

| Признак | Значение |
|---|---|
| Коммитов, менявших `*.cs`, за последние 60 | 60 (столько же, сколько `docs/`) |
| Изменения C# за последние 20 коммитов | +6 412 / −1 600 |
| Изменения `zere/` за последние 20 коммитов | +12 900 / −282 |

Функционально они уже разошлись. **Есть только в Python:** конспектор (`zere/core/conspect/`), рисование (Krita/Paint), роутер интентов Jev, MCP-плагины (браузер, заметки), обновление из GitHub, `voice_mode`, мост к C#-спикеру, выбор звукового устройства. **Есть только в C#:** нативное окно панели (`ZERE.App/Api/PanelWindow.cs`). Панель общая (`panel/dist` коммитится, CI проверяет его свежесть), поэтому фронтенд вынужден определять возможности бэкенда на лету (`aiSupport()` в `panel/src/api.ts`) — это уже признак расхождения, а не единого продукта.

Отдельно про релиз. `installer/ZereLauncher.bat` запускает сначала Python-редакцию (`.venv\Scripts\python.exe main.py`) и только потом `publish\app\ZERE.App.exe`; `installer/build-setup.ps1` наполняет дистрибутив через `git archive HEAD`, то есть **содержимое Setup.exe зависит от того, из какой ветки его собрали**. При этом `origin/main` — предок `python-port` (0 своих коммитов против 134), а README называет `python-port` «Python-версией». Что именно считается релизом, в документации не зафиксировано.

Цена поддержки видна на конкретном примере: нормализация русского текста для Silero реализована дважды — `zere/voice/silero/silero_text.py` (666 строк) и `ZERE.Voice/Text/SpeechText.cs`, с требованием паритета по разбивке предложений; сайдкары `tools/zere_chattts_server.py` и `tools/zere_silero_server.py` (259 строк каждый) после нормализации имён различаются лишь на 136 строк.

**Рекомендация:** явно назначить ведущую редакцию (судя по объёму и составу функций — Python), а вторую перевести в режим «поддерживается, новые подсистемы не портируются» либо в архив. Решение записать в README и AGENTS.md, иначе каждый следующий рефакторинг будет удваиваться.

### 5.3 `python tests/test_conspect.py` — «зелёный» при нуле выполненных тестов

Проверено запуском: обе новые тестовые подсистемы завершаются с кодом 0 и **не выполняют ни одного теста**:

```
$ python3 tests/test_conspect.py; echo exit=$?
exit=0
```

Причина: в репозитории де-факто две несовместимые конвенции запуска тестов.

- 21 файл имеет блок `if __name__ == "__main__"` с самодельным раннером, который вызывает `test_*()` **без аргументов** и поэтому принципиально не использует фикстуры pytest.
- `test_conspect.py` (37 обращений к `monkeypatch`/`tmp_path`) и `test_conspect_handler.py` (8) написаны на фикстурах и блока `__main__` не имеют.

Для files-with-fixtures запуск «как принято в репозитории» — тихий no-op: ни ошибки, ни выполнения, ни сообщения. Это ловушка иного класса, чем «тест не запускается»: и CI, и человек получают ложное подтверждение. Достаточно добавить в CI шаг `python -m pytest tests/ -q` (с установкой pytest) — и 257 тестов, включая всю новейшую функциональность, начнут реально исполняться.

### 5.4 Мёртвый код: ~1 300 строк в двух реализациях

Проверено по ссылкам на классы во всех `.py` (и отдельно — в `.cs`): следующие модули не используются нигде, кроме самих себя.

**Python (678 строк, 17 файлов):**

- `zere/core/context/` — `context_service.py`, `context_memory.py`, `context_item.py`, `context_type.py` (вся подсистема Context; живой только соседний `runtime_context.py`);
- `zere/tools/system/` — `power_controller.py`, `process_manager.py`, `system_info_service.py`, `process_command_router.py`, `process_command_type.py`;
- `zere/tools/windows/` — `screen_capture_service.py`, `audio_controller.py`, `file_controller.py`;
- `zere/memory/gaming/game_stats_repository.py` (и зависимый `game_stats_database.py`);
- `zere/tools/gaming/game_session.py`;
- `zere/tools/applications/installed_app_scanner.py`, `zere/tools/applications/indexing/app_index.py`.

**C# — 644 строки тех же классов** (`PowerController`, `ProcessManager`, `SystemInfoService`, `ScreenCaptureService`, `AudioController`, `FileController`, `ZERE.Core/Context/*`, `GameStatsRepository`, `GameSession`, `InstalledAppScanner`, `AppIndex`): в C# каждый из них тоже встречается ровно в одном файле — своём собственном. То есть это не потерянная проводка порта, а унаследованный от исходного C#-дизайна незавершённый замысел: действия питания реально исполняет `SafeActionManager._start(["shutdown", ...])`, дублируя логику мёртвого `PowerController`.

Плюс две «копии-близнеца»: `ProcessCommandRouter`/`ProcessCommandType` в `tools/system/` (мёртвая копия) и `tools/windows/` (рабочая), два класса `GameStat` (`memory/gaming/game_stat.py` и `tools/gaming/models/game_stat.py`). И пустой каталог `zere/voice/piper/` с одним `__pycache__`, оставшийся после замены Piper на ChatTTS.

### 5.5 Конвейер не сериализован между консолью, панелью и голосом

`ZereEngine.process()` вызывается из трёх независимых потоков: консольный цикл (`main.py`), обработчик панели (`zere/api/server.py:1556`, `ThreadingHTTPServer` — поток на запрос) и цикл голосового режима (`zere/api/server.py:167`). Точечные блокировки есть (`SafeActionManager` — `RLock`, `AiService` — `RLock`), но состояние обработчиков и инструментов (`GameTracker`, `DrawingService`, `MemoryExtractor`, `PluginCommandHandler`) не защищено, а общая очередь запросов отсутствует.

Практический сценарий: pending-действие (`shutdown`/`kill`), запрошенное из панели, потребляется словом «да» из консоли (или второй вкладкой) — то есть исполняется не тем контекстом, в котором его запрашивали. Для локального однопользовательского приложения это риск низкой вероятности, но именно такие гонки объясняют класс «странных» отчётов, которые трудно воспроизвести. Лечится одной очередью обработки (`queue.Queue` + один рабочий поток) вместо прямых вызовов `engine.process`.

## 7. Ограничения анализа

- C# не собирался (в окружении нет `dotnet`): выводы по C#-части — статические, по ссылкам и структуре.
- Не запускались Playwright-смок панели, живой голос (модели GigaAM/Silero и микрофон) и установщик в Windows.
- E2E-смок присутствует (6 спецификаций в `panel/e2e/`), но его фактическое прохождение в этом окружении не проверялось.
- Оценка «мёртвый код» сделана по статическим ссылкам на классы и модули; динамическая загрузка через `importlib` (внешние плагины) в расчёт не бралась.
