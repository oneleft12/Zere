# Анализ: как сделать голосового ИИ-ассистента ZERE быстрее и стабильнее

> **Статус на текущий момент.** Движок Piper заменён на ChatTTS (`zere/voice/chattts/`,
> `ZERE.Voice/ChatTts/`, сайдкар `tools/zere_chattts_server.py`); актуальное описание — `docs/TTS_CHATTTS.md`.
> Отчёт ниже сохранён как исторический: упоминания Piper, его замеры и ссылки на код относятся к Piper-эпохе.

**Дата:** 2026-09-28
**Область:** голосовой конвейер (wake word → STT → LLM → TTS), AI-клиент, старт приложения.
**Обе реализации:** C# (`ZERE.*`, .NET 10) и Python (`zere/`, `main.py` — дефолтный запуск через `ZERE.bat`). Большинство находок симметричны; расхождения отмечены явно.

## 2. Как устроен конвейер сейчас

```
Режим с wake word (дефолт):
  непр. запись (VAD по энергии) → речь → тишина 1.2 с → WAV → AudioPreprocessor (полный DSP-проход)
  → Whisper medium (транскрибация сегмента ≤9 с) → "Джарвис?" → запись команды
  → тишина 1.5 с → WAV → AudioPreprocessor → Whisper medium → ZereEngine
      → HandlerPipeline (9 хендлеров, регулярки) → AIHandler (промпт: вся память + 5 последних диалогов)
      → Ollama /api/generate (стрим читается ДО конца) → ПОЛНЫЙ ответ
  → SpeakAsync(полный текст) → Piper (попредложенное: WAV-файлы + DSP-файл на диск) или PocketTTS (PCM-поток)
```

Что уже сделано хорошо (не трогать): персистентный процесс Piper с ресинхронизацией по RIFF (`PiperService.cs:19-25`), попредложенное стриминг-воспроизведение Piper, потоковый PCM PocketTTS (`PocketTtsService.cs:100-146`) с `ResponseHeadersRead`, прогрев Piper в фоне (`PiperService.cs:119-134`), кольцевой буфер + адаптивный VAD (`ContinuousAudioRecorder.py` / `.cs`), кэш ответов Ollama в Python (`ollama_client.py:46`), предзагрузка Whisper в фоне **только в Python** (`main.py:115-119`), таймаут транскрибации 120 с **только в Python** (`whisper_service.py:31`).

## 4. Скорость: находки и что делать

### S1. Нет параллелизма LLM и озвучки (главный выигрыш)

**Симптом:** `zere.ProcessAsync()` возвращает **полностью** сгенерированный ответ, и только потом вызывается `SpeakAsync` (`Program.cs:274-282`, `main.py:410-417`). LLM генерирует 3–10 с, всё это время тишина.

**Решение — стриминг токенов в речь:**
1. `OllamaClient`: добавить `GenerateStreamAsync(...) → IAsyncEnumerable<string>` (C#) / генератор (Python) — сейчас `stream: true` объявлен, но поток читается до конца внутри клиента (`OllamaClient.cs:65,103-137`).
2. Новый оркестратор `StreamingSpeaker`: буферизует токены, отдаёт в TTS **первое предложение**, как только оно закончено (границы уже есть — `SpeechText.SplitSentences`, `SpeechText.cs:59`), дальше — попредложенное.
   - **PocketTTS:** проще всего — каждый следующий sentence уходит отдельным POST `/tts` в тот же `StreamPlayer` (сервер кэширует состояние голоса, `zere_tts_server.py:82-97`).
   - **Piper:** держать один `SynthesizeStreamAsync` на всю реплику; для стриминга LLM → Piper нужен API «добавь предложение в текущую сессию» (переписать гейт `PiperService.cs:155-228` на очередь строк).
3. Пока TTS играет первое предложение, LLM дописывает остальное — «первый звук» = первый токен + первое предложение + TTFB синтеза.

**Ожидаемый эффект:** −3…−8 с до первого звука.

### S2. Wake word через полную модель Whisper

**Симптом:** энергетический VAD детектирует **любую** речь, и на каждый всплеск уходит полная транскрибация сегмента до 9 с (`WakeWordDetector.cs:99-122`). Если в комнате говорит ТВ — Whisper крутится постоянно: CPU занят, STT команды и LLM замедляются, вентиляторы/троттлинг. Lожные срабатывания → лишние циклы.

**Решение (по возрастанию трудозатрат):**
1. **Быстро:** отдельная *tiny* Whisper для детектора (`whisperModelSize: "tiny"` уже поддержан в Python — `whisper_service.py:49-61`); инстанс — один на процесс. В 5–10 раз быстрее medium, память ~75 МБ.
2. **Правильно:** настоящий keyword-spotter со стримингом — **sherpa-onnx** (поддерживает C# и Python, есть готовые RU wake-word модели) либо Picovoice Porcupine. Почти нулевой CPU, детект без записи «сессий» вообще.
3. Гибрид: energy-VAD → tiny на окно 1–1.5 с (а не 9 с) → подтверждение слов «Джарвис» уже без полного пайплайна.

**Плюс:** сейчас после wake word сегмент команды пишется **повторно** тем же recorder — двухстадийная схема сохраняет, но окно для wake лучше сузить до 2–3 с (`MaxSegmentSeconds = 9f`, `WakeWordDetector.cs:31` — перебор для слова из 3 слогов).

### S3. Двойная и повторная загрузка Whisper

**Симптомы (проверено по коду):**
- `VoiceManager` держит свой `WhisperService` (`VoiceManager.cs:13`), `WakeWordDetector` — свой (`WakeWordDetector.cs:16`) → **две модели** одновременно (medium: ~1.5–3 ГБ RAM суммарно).
- `EnableWakeWord()` создаёт **новый** детектор при каждом цикле (`VoiceManager.cs:274-279`), а `Program.cs:189` зовёт его внутри `while (voiceMode)` → **каждая** команда оплачивает: новый recorder (повторная калибровка VAD 2 с, `ContinuousAudioRecorder.cs:225-240`) + новую ленивую загрузку модели Whisper в детекторе (`WhisperService.cs:31`). В Python та же история (`main.py:308` → `voice_manager.py:158-163` → `wake_word_detector.py:38`).
- `WhisperService` не реализует `IDisposable` — `WhisperFactory` (нативная память ggml) не освобождается вообще → утечка на каждом пересоздании.
- C# **не предзагружает** Whisper при старте (в Python есть `preload_whisper`, `main.py:115-119`) → первая транскрибация платит за загрузку.

**Решение:**
1. Один `WhisperService` на процесс: создать в DI/`VoiceManager`, передавать в `EnableWakeWord(config, whisper)`.
2. Один `WakeWordDetector` на сессию голосового режима (пересоздавать только при смене конфига); recorder не перезапускать между циклами (уже задумано в комментарии `WakeWordDetector.cs:55-57`, но ломается пересозданием детектора).
3. `WhisperService : IDisposable` + предзагрузка в фоне при старте (C#).

**Ожидаемый эффект:** −2…−5 с на каждой команде после первой; −1–2 ГБ RAM; нет «дыхания» памяти.

### S4. Фиксированные ожидания тишины и поллинги

**Симптомы:**
- Окончание речи жёстко: 1200 мс (wake, `WakeWordDetector.cs:89`) и 1500 мс (команда, `VoiceManager.cs:349`) — константа, не зависит от пауз в речи.
- Поллинги: `Task.Delay(200)` в ожидании старта речи (`VoiceManager.cs:333-337`), `ScanIntervalMs = 400` (`WakeWordDetector.cs:32`), `Task.Delay(100)` в консольном цикле (`Program.cs:228`) — суммарно до ~1 с чистой прослойки.
- Неиспользуемый путь `ListenAsync` пишет **фиксированные 5 с** (`VoiceManager.cs:106` → `AudioRecorder.cs:15`), хотя `RecordWithVadAsync` уже написан.

**Решение:**
- Адаптивный endpointing: пауза в речи > 500–700 мс при высокой уверенности VAD → стоп; максимум 800 мс. Ещё лучше — Silero VAD (встроен в faster-whisper: `vad_filter=True`, `whisper_service.py:214`) как endpointer: убирает и ожидания, и шумовые срабатывания.
- Событийная петля вместо поллинга: `ContinuousAudioRecorder` уже считает `_isSpeech` — публиковать `SpeechStarted/SpeechEnded` события (C# `event`, Python `queue`), слушатель реагирует мгновенно.
- Всегда использовать VAD-рекордер (и в `ListenAsync`, и в панели).

**Ожидаемый эффект:** −1.5…−2.5 с.

### S5. LLM: keep_alive, лимиты, прогрев, таймаут

**Симптомы:**
- В запросе только `temperature` (`OllamaClient.cs:46-55`, `ollama_client.py:85-91`). Нет:
  - `keep_alive: -1` (или большой) — Ollama по умолчанию выгружает модель через 5 мин простоя → следующий запрос платит загрузку (+2…5 с). **Проверить фактический keep_alive в консоли `ollama ps`.**
  - `num_predict` — голосовой ответ не должен быть 300 токенов; 80–120 токенов + инструкция «отвечай короткими предложениями» в системный промпт для голосового режима.
  - `num_ctx` — считать под память+историю.
  - прогрев при старте (POST-заглушка на 1 токен) — параллельно с DependencyChecker.
- Таймаут **10 минут** (`OllamaClient.cs:19`) — для голоса недопустимо: пользователь ждёт молча. 30–60 с + быстрый фолбэк «модель не отвечает».
- `PostAsync` без `ResponseHeadersRead` (`OllamaClient.cs:62`) — весь NDJSON-поток буферизуется целиком, «стриминг» внутри клиента бессмысленен (находка аудита P2-11); `HttpResponseMessage` не dispose-ится.
- `ContextBuilder.BuildMemory` берёт **всю** память без лимита (`ContextBuilder.cs:19`) → промпт растёт со временем → LLM медленнее и дороже, есть и prompt-injection (аудит P2-6). Лимит: последние/самые релевантные N фактов, ~1000–1500 символов.
- Python-кэш ответов LRU (`ollama_client.py:46`) есть, в C# нет — ок для локальных повторов.

**Решение:** параметры в `config.json` (`llmKeepAlive`, `llmMaxTokens`, `llmTimeoutSeconds`), дефолты `keep_alive: -1`, `num_predict: 96` (голос), таймаут 60 с, прогрев на старте, `ResponseHeadersRead` + `IAsyncEnumerable` (заодно закрывает S1), обрезка памяти.

**Ожидаемый эффект:** −2…−5 с на холодной модели; стабильнее время ответа; короче ответы.

### S6. Piper: файловый I/O на каждое предложение, DSP-файл, рестарты

**Симптомы:**
- Каждое предложение пишется **на диск** (`PiperService.cs:544-551`), затем `AudioProcessor.Process` читает его, DSP-обрабатывает и пишет **ещё один** файл (`VoiceManager.cs:173-183`) — на каждое предложение 2× чтение + 2× запись. Потом удаление. На HDD/медленном SSD это десятки-сотни мс между предложениями и мусор в папке.
- Смена скорости/паузы = **рестарт процесса** Piper с перезагрузкой модели (`PiperService.cs:261-289`).
- `FrameTimeout` 30 с (`:43`) — при зависании юзер ждёт полминуты.

**Решение:**
- Перевести Piper на тот же путь, что Pocket: читать WAV-кадр из stdout и **потоково** кидать PCM в `StreamPlayer` (формат из `fmt`-чанка уже разбирается в `ReadFrameAsync`) — ноль файлов на диске.
- DSP (EQ/компрессия) — над буфером в памяти, в том же потоке (numpy/NAudio), либо отключить по умолчанию для голосового режима.
- Рестарт при смене параметров — только если реально меняется `length_scale`/`sentence_silence` (уже есть проверка `:266-268` — ок), не перезапускать на смене голоса без нужды.
- Снизить `FrameTimeout` до ~10 с для интерактивного режима.

### S7. Старт приложения

- `DependencyChecker.RunAll()` на **каждом** старте (`Program.cs:91-92`, `main.py:48-49`) — субпроцессы, HTTP-проверки; кэшировать результат (валидность 24 ч) или проверять в фоне.
- PocketTTS: `WaitUntilReady` — sync-over-async `GetAwaiter().GetResult()` + `Thread.Sleep(500)`, до **6 минут** блокировки (`PocketTtsService.cs:78-81,244-288`). Перевести на `async/await` и запускать **в фоне**, пока консольный цикл уже работает; первый ответ без TTS → текст, потом включается.
- C#: прогрев Whisper в фоне (см. S3), прогрев Ollama (S5) — параллельно, не последовательно.

**Ожидаемый эффект:** старте «готов через 2–3 с», а не «через 10–30 с».

### S8. Бардж-ин (перебивание) отсутствует

Пока ZERE говорит, микрофон не слушает: wake-цикл запускается только после полного `SpeakAsync` (`Program.cs:282→191`). Пользователь вынужден ждать конца реплики.

**Решение (по сложности):** (1) хотя бы останавливать озвучку по нажатию Enter/кнопке в панели (API `StopSpeaking` уже есть, `VoiceManager.cs:262-267`); (2) полноценный бардж-ин — слушать во время playback и обрывать TTS, но нужно подавление эха (AEC) — NAudio умеет через WASAPI AEC; это этап 3, не раньше стабилизации S1–S7.

## 5. Стабильность: находки и что делать

### F1. Ошибка микрофона роняет приложение
Запись вне try/catch в C# (`AudioRecorder.cs:44-74`, вызовы `Program.cs:309`) — исключение (занятый устройством, отключенный микрофон) завершает процесс. В Python части это закрыто (`voice_manager.py:101-106`), в C# — нет (аудит P1-5).
**Решение:** try/catch вокруг всей записи + фолбэк «текстовый ввод» (паттерн уже есть), ретрай инициации устройства 1–2 раза.

### F2. Откат pocket→piper работает только один раз при старте
`IsAvailable` выставляется при `Initialize` (`PocketTtsService.cs:47-94`); если Python-сервер TTS умер позже — логируется предупреждение (`:214-218`), но **каждый** следующий ответ уходит в текст (поток бросает исключение, `VoiceManager.cs:134-152` печатает фолбэк), и обратного переключения на Piper нет. Обещание AGENTS.md «откат при сбоях» не выполняется (аудит P1-5).
**Решение:** health-loop (GET `/health` раз в N сек в фоне) + авто-restart сервера (1–2 попытки) + при неудаче переключить `_pocket.IsAvailable = false` **навсегда до следующего старта** — тогда `SpeakAsync` сам уйдёт на Piper (`:134-136`). Плюс обрабатывать `Exited` не только логом.

### F3. Расход и утечка памяти
- Две (C#/Python) и более моделей Whisper одновременно (S3); каждое пересоздание детектора = новый инстанс.
- `WhisperService` не dispose-ится (C#, `WhisperService.cs`) — нативная память ggml утекает.
- `StreamPlayer`: буфер на 2 минуты (`StreamPlayer.cs:23`) — ~4 МБ, приемлемо; но `_activePlayer` перекрывается новым при прерывании — `SpeakAsync` останавливает старый (`:127`), ок.
**Решение:** один инстанс STT на процесс, `IDisposable`, диагностика RSS в лог раз в сессию.

### F4. Гонки панель ↔ консоль на голосовых ресурсах
`PanelServer` зовёт `_voice.ListenAsync()` / `SpeakAsync()` (`PanelServer.cs:1404,1472,1493`; Python `server.py:950,998,1011`) **параллельно** с консольным циклом, при этом:
- `RecordAsync` пишет в **фиксированный** `voice/input/record.wav` (`AudioRecorder.cs:24`) → два параллельных вызова перезапишут файл друг другу и выбросят исключение;
- `VoiceManager._player` один на все вызовы.
**Решение:** имена файлов — GUID/temp; семафор на «запись» и на «озвучку» (`SemaphoreSlim`); либо весь голос через единую очередь команд.

### F5. VAD: калибровка и пороги
- Адаптивная калибровка первые 2 с (`ContinuousAudioRecorder.cs:225-240`): если в этот момент шумно — порог «шум × 2» застревает высоким (комментарий в коде это признаёт) → микро-команды не распознаются; если тихо — ловит шум.
- `DeviceNumber = 0` хардкод (`:77`, также `AudioRecorder.cs:37`) — выбор микрофона невозможен, смена устройства по умолчанию = тишина.
- Энергетический VAD не отличает речь от ТВ/музыки (см. S2).
**Решение:** ручной override порога в настройках (`SetThreshold` уже есть), пере-калибровка по кнопке, номер устройства в `config.json`, Silero VAD как основной детектор (устойчив к фону).

### F6. Whisper: таймаут и качество
- **C# не имеет таймаута транскрибации** (весь `WhisperService.cs`, 84 строки) — зависший вызов = вечное «Распознаю…». В Python таймаут 120 с есть (`whisper_service.py:31`), но 120 с для голоса — слишком; 15–20 с + фолбэк.
- medium на CPU — медленно; для коротких команд хватает small/base int8 (`whisperModelSize` уже поддержан). Эвристика: wake → tiny, команда → base/small, длинная диктовка → medium.
- `beam_size` по умолчанию (5) — для команд 1 ускоряет в ~2× (`model.transcribe(..., beam_size=1)`), `condition_on_previous_text=False` борется с галлюцинациями-петлями на коротких отрезках, `initial_prompt="Джарвис, ..."` улучшит RU-распознавание имени.
- Предобработка `AudioPreprocessor` на **каждой** транскрибации, включая wake-сегменты (`WhisperService.cs:45`) — полный DSP-проход + запись копии файла. Сделать опциональной (on-by-default только для длинных/грязных записей) или in-memory.

### F7. Piper-процесс: рассинхронизация и зависания
Механизм в целом крепкий (RIFF-ресинхронизация, рестарт при ошибке, `stderr`-читалка). Остатки:
- чтение кадра с таймаутом 30 с и `TimeoutException` → рестарт процесса посреди реплики (фолбэк на текст) — нормально, но 30 с слишком для голоса (F6-паттерн: 10 с);
- `SetInferenceParams`/`SetVoice` рестартуют процесс без гейта с `SynthesizeStreamAsync` — **гонка**: смена личности во время озвучки может убить процесс под активным чтением. Беречь `_processLock` уже есть, но активный `ReadFrameAsync` получит `IOException` → текст-фолбэк. Решение: отложить смену голоса до конца реплики (флаг «pending voice»).
- мусор `output_*.wav` при падении чистится только при старте (`CleanupOldOutputs`, `:606`) — чистить и после каждой реплики (в новой схеме S6 файлов не будет вовсе).

### F8. TTS-сервер (Python): ненадёжности
- `ProbeReady` примется за **любой** процесс, занявший порт 8471 с валидным `/health` (`PocketTtsService.cs:65-72,223-242`) — аудит P2-9; добавить проверку поля (`"server":"zere-tts"` в `/health`).
- `ThreadingHTTPServer` без лимита потоков и без таймаута чтения сокета; `SYNTH_LOCK` сериализует всё — два конкурентных `/tts` (панель + консоль) встают в очередь (OK), но сломанный клиент может держать замок. Добавить `socket.settimeout`, лимит длины текста (например, 2000 символов), `daemon_threads`.
- Рестарт сервера после падения — см. F2.

### F9. Нет измеримости (без этого нельзя итерировать)
Сейчас ни один этап не логирует длительность. Добавить единый префикс `[Perf]`:
`STT=…мс (загрузка модели: …мс) | LLM first token=…мс | LLM total=…мс | TTS first audio=…мс | end-of-speech→first audio=…мс`.
В Python — через `time.perf_counter`, в C# — `Stopwatch`; агрегировать последнюю сессию и показывать в панели (экран «Голос» уже есть). Это этап 0: **без замеров все оценки выше — гипотезы.**

## 10. DSP-обработка озвучки: разбор «металлического» звука

| Причина | Где было | Почему звучало «металлически» |

## 11. Почему исправление не помогло сразу: ресемплинг у аудио-движка

После правок §10 звук «остался таким же». Причина — вторая половина той же
проблемы, и первая попытка её только усугубила.

### Ключевой факт: панель играет мимо микшера

`zere/voice/audio/audio_player.py` играет через **sounddevice → PortAudio →
WASAPI напрямую**, минуя системный микшер с его качественным ресемплером.
Устройство по умолчанию у пользователя — **Sennheiser USB headset, 44100 Гц**.

- **До правок:** `AudioProcessor` апсемплил 22050 → 44100, то есть отдавал
  файл ровно в нативную частоту устройства — PortAudio играл без конверсии,
  но с «металлом» от наивной интерполяции.
- **После §10 (ошибка):** файл оставался 22050 Гц, а устройство 44100 →
  конвертировать стал PortAudio своим слабым ресемплером. Артефакт не исчез,
  а переехал из файла в поток. Поэтому «сырой» и «новый» файлы **звучали
  одинаково в плеере**, но одинаково плохо — в панели.

Вывод: мало убрать ресемплинг — важно, **чтобы его делал кто-то с хорошим
фильтром**. Отдать эту работу аудио-движку нельзя.

### Решение

Ресемплим сами, но качественно: оконный sinc (Kaiser, β=8, 64 тапа,
`cutoff = min(1, to/from)` для анти-алиасинга, нормировка на сумму весов):

- C# — `AudioProcessor.ResampleSinc` + `BesselI0`/`Sinc`;
- Python — `_resample_sinc` + `_kaiser_window`/`_bessel_i0`.

Целевая частота определяется у устройства, а не хардкодится:

- C# — `VoiceManager.ResolveOutputSampleRate()`: `MMDeviceEnumerator` →
  `GetDefaultAudioEndpoint(Render, Multimedia)` → `AudioClient.MixFormat.SampleRate`;
- Python — `voice_manager.output_sample_rate()`: `sd.query_devices(default)[
  "default_samplerate"]`;
- фолбэк в обоих случаях — `AudioProcessor.DefaultSampleRate` (44100).

### Замеры (файл `voice/tts_compare/`)

| Файл | Частота | Энергия > 11 кГц |
|---|---|---|
| `1_piper_syroy.wav` — сырой piper | 22050 Гц | −53.1 дБ |
| `3_staryy_DSP.wav` — старый (линейная интерполяция) | 44100 Гц | **−27.8 дБ** |
| `4_kachestvennyy_44100.wav` — эталонный sinc-апсемпл | 44100 Гц | −53.9 дБ |
| `5_ITOG_sinc_44100.wav` — итоговая цепочка | 44100 Гц | **−53.9 дБ** |

Итог: устройство получает родные 44100 Гц (PortAudio не конвертирует), а
паразитная энергия выше 11 кГц подавлена на 26 дБ сильнее, чем у старого
апсемпла. Проверено на живом устройстве: `device=44100 Гц → processed=44100 Гц`.


## 12. Выбор аудиоустройства: WASAPI, частота и ошибка -9997

Симптом из панели («Режим голоса → Состояние режима: ошибка»):

```
Error opening InputStream: Invalid sample rate [PaErrorCode -9997]
```

Причина: порт на sounddevice стал открывать микрофон в бэкенде **WASAPI**
(низкая задержка), а WASAPI в shared-режиме принимает только частоту микшера
Windows. Whisper/GigaAM требуют 16 кГц, микрофон Sennheiser USB headset
заявляет 48 кГц, микшер работает на 44.1 кГц — поток не открывался вовсе.

Замеры (Windows 11, Sennheiser USB headset, sounddevice 0.5.6, живые
устройства 27 — вход, 22 — выход):

| Проверка | Результат |
|---|---|
| `check_input_settings(27, 16000)` | **-9997** |
| `check_input_settings(27, 16000, auto_convert=True)` | OK |
| `check_input_settings(27, 48000)` | OK |
| `check_output_settings(22, 44100)` | OK |
| `check_output_settings(22, 48000)` | **-9997** |

Важная деталь: `default_samplerate` WASAPI-устройства врёт — микрофон
заявляет 48 кГц, а микшер живёт на 44.1 кГц (48000 без `auto_convert` тоже
падал). Поэтому «взять частоту устройства» — не решение.

Решение (`zere/voice/audio/audio_device.py`):

- `input_options`/`output_options` отдают готовые аргументы открытия потока:
  WASAPI-устройство + `sd.WasapiSettings(auto_convert=True)` (флаг
  `paWinWasapiAutoConvert` — системный ресемплер Windows), а если вариант не
  поддержан (`check_input_settings`/`check_output_settings`) — устройство по
  умолчанию (MME: PortAudio ресемплирует сам);
- все точки захвата и вывода используют эти хелперы (`AudioRecorder.record`,
  `record_with_vad`, `ContinuousAudioRecorder.start_continuous_recording`,
  `AudioPlayer.play`);
- сбой захвата больше не убивает голосовой режим навсегда: `VoiceModeRunner`
  пишет `lastError`, делает паузу и слушает дальше (раньше состояние
  залипало в `error` до перезапуска ZERE);
- при перенаправленном выводе (`ZERE.bat > log.txt`, cp866/cp1251) эмодзи
  в принтах падали `UnicodeEncodeError` — в аудио-пути это выглядело как
  «сбой микрофона»; `configure_console_encoding()` (`zere/core/console.py`)
  заменяет непредставимые символы на «?».

Тесты: `tests/test_audio_device.py` (12: регрессия -9997 на фейковом тракте +
живое открытие 16 кГц) и `tests/test_voice_mode.py` (4: сбой записи и озвучки
не убивает цикл).
## 13. «Очень компрессированный звук»: убран DSP-компрессор

Жалоба: озвучка звучит перекомпрессированной (зажато, ровно, «стеной»).

Причина — в DSP-цепочке `AudioProcessor` (одинаковой в Python и C#): компрессор
2.5:1 при пороге **−18 dBFS** плюс **нормализация всего файла** на −3 dBFS.
Порог −18 dBFS ниже уровня почти всей речи, поэтому сжатие работало постоянно,
а нормализация поднимала громкость уже сжатого материала — динамика «зажималась».

Замеры (оффлайн, `voice/tts_compare/1_piper_syroy.wav`, 5.46 с, без обращения к
звуковым устройствам):

| Вариант | Пик | RMS | Разброс кратковременной RMS (p95−p5) |
|---|---|---|---|
| сырой Piper | 0.00 dBFS | −19.1 dBFS | 25.7 дБ |
| старая DSP (с компрессором) | −3.00 dBFS | −24.1 dBFS | **23.8 дБ** |
| новая DSP (без компрессии) | −1.00 dBFS | −21.3 dBFS | **25.3 дБ** |

То есть компрессор действительно сжимал динамику (25.7 → 23.8 дБ) и заодно
уводил громкость вниз на 5 дБ RMS. Новая цепочка возвращает динамику к
исходной (25.3 дБ) и звучит на 2.7 дБ громче.

Что осталось в цепочке (всё, что не портит динамику):

- качественный sinc-ресемплинг до частоты устройства (§11) — он снимает
  «металл» от ресемплера аудио-движка;
- HPF 75 Гц (гул/румбл), корректирующий EQ (350 Гц −3 дБ, 6.5 кГц −2.5 дБ) и
  «кинематографичный» EQ ±2 дБ;
- страховка по пикам −1 dBFS — **только ослабление**: тихие места больше не
  подтягиваются вверх (иначе это снова выравнивание громкости);
- мягкий лимитер −0.5 dBFS (срабатывает только на пиках).

Изменение внесено в обе редакции: `zere/voice/audio/audio_processor.py` и
`ZERE.Voice/Audio/AudioProcessor.cs` (метод `ApplyCompressor` заменён на
`AttenuatePeak`). Сравнить «до/после» на слух можно тумблером «DSP-обработка»
на экране «Голос»: выключенный — сырой Piper без обработки.

Живые тесты, трогающие звуковые устройства (микрофон/наушники), теперь
запускаются только по `ZERE_LIVE_AUDIO=1` — по умолчанию тесты работают на
фейковом тракте и устройств не касаются.
## 14. Шипение и «металл»: мягкий ФНЧ 8 кГц

Жалоба: озвучка «шипит/свистит», отдаёт «металлом». Замер сырого вывода Piper
(`voice/tts_compare/1_piper_syroy.wav`) показывает, что шумовая составляющая
живёт выше 6 кГц: спектральная плоскостность в полосе 4–10 кГц — 0.44
(близко к шуму), а на 8–11 кГц приходится 0.56 % всей энергии. Это свойство
модели, а не тракта: DSP лишь слегка менял пропорции.

Решение — мягкий ФНЧ 2-го порядка (RBJ, Баттерворт) на 8 кГц в DSP. АЧХ:
3 кГц −0.05 дБ, 6 кГц −1.0 дБ, 8 кГц −3.0 дБ, 11 кГц −6.4 дБ: присутствие и
разборчивость не страдают, а шипящая полоса уходит вниз.

| Вариант | 3–6 кГц | 6–8 кГц | 8–11 кГц | >11 кГц |
|---|---|---|---|---|
| сырой Piper | 2.23 % | 1.49 % | 0.558 % | 0.0005 % |
| старая DSP (компрессор, без ФНЧ) | 3.28 % | 1.45 % | 0.706 % | 0.0007 % |
| новая DSP (без компрессии + ФНЧ 8 кГц) | 2.70 % | **0.89 %** | **0.243 %** | 0.0001 % |

Если шипение всё же останется, источник — сама модель Piper
(`ru_RU-ruslan-medium`, 22050 Гц); альтернативы — другой голос, PocketTTS или
тумблер «DSP-обработка» для сравнения с сырым синтезом.

## 15. Озвучка на C#: хелпер ZERE.Speaker

По запросу «озвучка на C#, а не на Python» DSP и вывод звука вынесены в
отдельный C#-процесс `ZERE.Speaker` (NAudio: `WasapiOut`, откат на WinMM).
Ядро, панель и распознавание остаются на Python.

Как это работает:

- хелпер поднимается **один раз** в режиме `host` и общается строками JSON
  (запрос на строку, ответ на строку): `speak` (DSP + вывод), `stop`
  (обрыв фразы), `ping`, `quit`. Диагностика хелпера идёт в stderr, поэтому
  stdout остаётся чистым протоколом;
- Python-мост — `zere/voice/audio/csharp_speaker.py`; `VoiceManager.speak`
  сначала пробует C#, а при отсутствии сборки/крахе/таймауте озвучивает сам
  через sounddevice (`ZERE_SPEAKER=python` — принудительный Python);
- DSP один и тот же код: `ZERE.Voice/Audio/AudioProcessor.cs` подключён в
  хелпер ссылкой на исходник, поэтому расхождение между редакциями
  невозможно. Паритет проверен замером: на одном входном файле Python и C#
  дают одинаковые пик (−1.00 dBFS) и полосы энергии (2.70 / 0.89 / 0.243 %);
- сборка: `dotnet publish ZERE.Speaker -c Release -o publish\speaker`
  (это делает `install.ps1`; для Python-редакции — необязательный шаг, при
  отсутствии .NET SDK озвучка просто остаётся на Python);
- тесты `tests/test_csharp_speaker.py` (9) работают без звуковых устройств:
  протокол проверяется фейковым хелпером `tests/fake_speaker.py`, а настоящий
  хелпер — в режиме `dry` (DSP считается, звук не играется).
