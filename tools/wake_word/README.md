# Обучение слова-триггера «зере» (wake word)

Тулчейн обучает крошечный KWS-детектор (keyword spotting) на русское слово
**«зере»** и выпускает **один ONNX-файл**, который читают обе редакции ZERE
(Python `zere/voice/wakeword/` и C# `ZERE.Voice/WakeWord/`).

Готовый движок берём не случайно: русских KWS-моделей у sherpa-onnx и Vosk
нет, а гонять полный STT каждые 40 мс — это сотни миллисекунд. Своя CNN на
~58 тыс. параметров (≈0.5 МБ) считает окно за единицы миллисекунд на CPU.

---

## 1. Контракт модели (заморожен)

| Что | Значение |
|---|---|
| Вход | `audio`, float32, `(batch, 16000)`, значения в [-1, 1] |
| Выход | `score`, float32, `(batch, 1)` — сигмоида-вероятность слова в окне |
| Частота | 16000 Гц |
| Окно | 16000 сэмплов (ровно 1.0 с) |
| Шаг рантайма | 640 сэмплов (40 мс) — в графе окно фиксировано |
| Opset | 17 |

**Весь DSP внутри графа:** STFT (n_fft=256, окно Ханна 256, hop=160,
`center=False` → 99 кадров) → мощность (129 бинов) → 40 мел-фильтров
(mel-шкала и area-нормировка как в librosa `htk=False, norm='slaney'`) →
`ln(x + 1e-6)` → пер-оконная нормализация `(x − mean) / (std + 1e-5)` по всем
40×99 значениям окна.

Почему так: C#-редакции не нужно повторять эту математику. Ошибка в DSP на
одной стороне означала бы, что модель работает в Python и молчит в C#.

Две детали, которые легко испортить при доработке:

* **STFT считается `Conv1d` с явной матрицей базиса ДПФ**, а не `torch.stft` /
  `torch.fft.rfft`. FFT-операторы экспортируются в ONNX как `DFT`/`STFT`,
  поддержка которых в onnxruntime различается по версиям; свёртка есть везде.
  Корректность базиса проверяет `self_test.py` — сверяет признаки с
  независимой реализацией на numpy-FFT.
* **Ось 0 — динамическая (батч), ось 1 — фиксированная (16000).**

Проверка графа вручную:

```bash
python -m tools.wake_word.evaluate --onnx ZERE.Voice/WakeWord/models/wake_zere.onnx
```

### Манифест

Рядом с моделью лежит `wake_zere.json` — ровно эти ключи читает рантайм:

```json
{"engine":"onnx-kws","format":1,"word":"зере","sample_rate":16000,
 "window_samples":16000,"hop_samples":640,"threshold":0.7,
 "min_consecutive":2,"cooldown_ms":1800,"input_name":"audio",
 "output_name":"score","trained_at":"2026-10-…",

            "val_recall":0.97,"val_fa_per_hour":0.4},
```

## 2. Установка зависимостей

```bash
python -m pip install numpy                    # обязательна
python -m pip install onnxruntime              # обязательна для eval и рантайма
python -m pip install torch                    # обязательна для train/eval
python -m pip install onnx                     # только для ЭКСПОРТА ONNX из torch
python -m pip install sounddevice              # только для записи с микрофона
python -m pip install soundfile                # опционально (экзотические форматы)
```

**`onnx` и `onnxruntime` — разные пакеты.** `onnxruntime` исполняет готовую
модель (нужен рантайму и `evaluate`), а `onnx` умеет её сериализовать, и без
него `torch.onnx.export` падает с `Module onnx is not installed!`. В рантайме
`onnx` не нужен: если экспорт сейчас не требуется, обучайте с `--no-export`
(чекпойнт `best.pt` и метрики всё равно сохранятся), а модель возьмите из
готового прогона.

Про torch:

* GPU (CUDA): `python -m pip install torch --index-url https://download.pytorch.org/whl/cu124`
* CPU (работает, но медленнее): `python -m pip install torch --index-url https://download.pytorch.org/whl/cpu`
* В проекте torch уже приходит с ChatTTS (`requirements.txt`), так что обычно
  отдельная установка не нужна. Скрипты **не требуют** torch для сбора данных:
  `record_positives`, `synth_positives`, `build_negatives` работают и без него
  (torch нужен только для синтеза и для train/eval).

Проверить, что всё на месте, не трогая реальные данные:

```bash
python -m tools.wake_word.self_test      # печатает OK, ~3 с
```

Раскладка (создаётся автоматически, в git не попадает):

```
├── negative_room/*.wav    своя комната/ТВ/YouTube
├── negative_hard/*.wav    похожие слова (зера, зери, зори, зрение, озеро…)

├── splits.json            детерминированное разбиение train/val/test
```

### Сколько чего нужно

| Категория | Минимум | Хорошо | Зачем |
|---|---|---|---|
| `positive` (живые) | 100 | 300+ | правда о вашем микрофоне и манере речи |
| `positive_synth` | 1000 | 3000 | разнообразие тембра/темпа без ручной работы |
| `negative_speech` | 0.5 ч | 3 ч | чтобы не просыпаться на обычную речь |
| `negative_noise` | 0.5 ч | 2 ч | музыка, техника, улица |
| `negative_room` | 0.2 ч | 1 ч | **ваша** комната и ТВ — самое ценное |
| `negative_hard` | 100 файлов | 500 | «зера/зори/озеро» — главный источник ложных срабатываний |

Часы важны, а не число файлов: FA/час считается по непрерывному аудио.

### 3.1 Живые записи (100+)

```bash
python -m tools.wake_word.record_positives --count 100
```

Скрипт подсказывает условие для каждой записи и чередует их: обычно, близко,
далеко, тихо, громко, быстро, медленно, с шумом. Разные условия — это и есть
ценность живого набора; 100 записей, сказанных одинаково, почти бесполезны.

* `--device N` — выбрать микрофон (список печатается при запуске);
* `Enter` — принять запись, `r` — перезаписать, `q` — выйти;
* слишком тихие записи и клиппинг отклоняются с объяснением;
* тишина по краям обрезается автоматически.

Уже записанные файлы (телефон, диктофон) импортируются без микрофона:

```bash
python -m tools.wake_word.record_positives --from-files D:/records
```

> В WSL микрофон по умолчанию не виден. Записывайте в Windows.

### 3.2 Синтез позитивов

```bash
python -m tools.wake_word.synth_positives --count 3000
python -m tools.wake_word.synth_positives --count 500 --device cuda
```

Использует проектный Silero v5 (`zere/voice/silero/`, голоса baya, xenia,
kseniya, aidar, eugene), с фолбэком на прямую загрузку `v5_5_ru.pt` из
`ZERE.Voice/Silero/`. Вариации: темп 0.8–1.2, питч ±15 %, громкость, паузы
до/после слова, подмешивание шума своей комнаты.

Темп и питч **связаны** — это одна операция («проиграть быстрее/медленнее»),
а не два независимых рычага: настоящий независимый сдвиг питча требует
phase-vocoder и новых зависимостей. Для wake word связка даже полезна.

Текст не обрастает лишними словами: «эй, зере» научило бы модель опираться на
«эй», и одиночное «зере» перестало бы ловиться.

### 3.3 Негативы

```bash
# свои аудио: YouTube-рипы, запись комнаты, подкасты (рекурсивно)
python -m tools.wake_word.build_negatives --from-dir D:/youtube-rips
python -m tools.wake_word.build_negatives --from-dir ./my-room --category negative_room

# похожие слова (синтез)
python -m tools.wake_word.build_negatives --hard --hard-count 40

# MUSAN (CC BY 4.0), ~11 ГБ — ТОЛЬКО по этому флагу, по умолчанию не качается
python -m tools.wake_word.build_negatives --download musan --musan-limit 200

# пересобрать разбиение
python -m tools.wake_word.build_negatives --split
```

По умолчанию **ничего не скачивается**: сеть трогается только явным флагом.
Длинные файлы не режутся на куски — обучение читает окна с диска, а FA/час
считается по непрерывному аудио.

### 3.4 Разбиение: что оно гарантирует

`splits.json` строится по группам, и это не формальность:

* **Изоляция.** Записи одной сессии не разъезжаются по train/val/test. Живые
  записи группируются по «каталог + имя без номера», негативы — по файлу
  (каждый файл-источник независим). Без этого почти одинаковые окна попали бы
  и в обучение, и в тест, а метрики оказались бы завышенными: модель
  «узнавала» бы микрофон, а не слово.
* **Покрытие.** В каждом из train/val/test есть и позитивы, и негативы. Если
  этого достичь нельзя (например, все записи лежат в одной плоской папке и
  образуют одну группу), сборка разбиения **падает с объяснением**, что
  сделать: разложить записи по подпапкам-сессиям (`positive/session1/`,
  `positive/session2/`) или записать больше.

Это сделано намеренно: разбиение без позитивов даёт `recall = 0` по пустому
множеству, и такое «нулевое» качество легко принять за слабую модель, хотя
дело в раскладке файлов. `self_test` проверяет обе гарантии, а также то, что
неполное разбиение действительно падает с понятным текстом.

> **Негатив — это окно, где слова нет вовсе.** Запись, где «зере» сказано в
> начале, а дальше тишина, негативом НЕ является: обучение на таком окне учит
> модель игнорировать само слово. Именно поэтому позиционирование слова в
> позитивах такое важное (см. §4).

## 4. Обучение

```bash
python -m tools.wake_word.train --device cuda                 # GPU
python -m tools.wake_word.train --device cpu --epochs 10      # CPU (медленно)
```

Что происходит: аугментации на лету (gain −20…+6 дБ, шум SNR 0…25 дБ, скорость
0.85–1.15, реверберация, SpecAugment 2 freq-маски ≤8 и 2 time-маски ≤10
кадров) → обучение на окнах «слово/не слово» → после каждой эпохи подсчёт
recall и FA/час на `val` → early stopping по метрике «минимальный FA/час при
recall ≥ 0.97» → экспорт ONNX + манифест.

Ключевые аргументы:

| Аргумент | Смысл |
|---|---|
| `--epochs 40` | максимум эпох (обычно останавливается раньше) |
| `--batch-size 64` | размер батча |
| `--epoch-size 4000` | окон в эпохе, независимо от размера корпуса |
| `--neg-per-pos 2` | баланс 1:2 (допустимо 1…3) |
| `--pos-weight 1.0` | вес положительного класса в BCE |
| `--loss bce\|focal` | BCE (обычно) или focal при сильном перекосе |
| `--patience 6` | эпох без улучшения до остановки |
| `--target-recall 0.97` | цель по recall для early stopping |
| `--device cuda\|cpu` | устройство (без CUDA честно откатится на CPU) |

Почему баланс ограничен 1:1…1:3: при 1:1 модель недоучивается на фоне и
пропускает слово, при 1:3 начинает срабатывать на обычной речи.

Позиционирование слова (спецификация): у 80 % позитивов конец слова попадает
в [0.80, 1.00] с окна, у 20 % — в [0.65, 0.80]; остальное — фон/тишина. Слово
никогда не оказывается раньше 0.65 с: детектор смотрит последнюю секунду, и
«слово в начале окна» для него уже в прошлом.

Артефакты прогона — в `data/wakeword/runs/<ts>/`: `best.pt`, `last`/`final`,
`metrics.csv` (по эпохам), `model.onnx`, `manifest.json`, `eval_report.md`.

## 5. Порог

Порог **не угадывается вручную**: `train.py` перебирает сетку порогов на `val`
и берёт тот, у которого **минимальный FA/час при recall ≥ 0.97**. Выбранное
значение попадает в манифест.

```
Порог (val, recall ≥ 0.97): 0.70
val:  recall=0.9812  FA/час=0.402
test: recall=0.9750  FA/час=0.531
```

Порог выбирается на `val`, а метрики в манифест пишутся с `test`: выбор по
`test` превратил бы held-out в часть обучения и метрики перестали бы что-либо
значить. Полная таблица «порог → recall / FA/час» — в `eval_report.md`.

Имя файла — `wake_<слово>.onnx`, где слово транслитерировано в латиницу
(«зере» → `zere`). Обе редакции ищут модель именно там.

Отдельного шага «установить модель» нет: `train.py` публикует её сам. Если
нужно положить модель в другое место — `--model-dir <папка>`.

## 7. Проверка

```bash
# оценка готовой ONNX-модели (torch не нужен)
python -m tools.wake_word.evaluate --onnx ZERE.Voice/WakeWord/models/wake_zere.onnx

# оценка чекпойнта с отчётом в каталог прогона
python -m tools.wake_word.evaluate --run data/wakeword/runs/20261008-2100

# жёстче: считать срабатыванием только 2+ окна подряд (как в рантайме)
python -m tools.wake_word.evaluate --onnx ZERE.Voice/WakeWord/models/wake_zere.onnx \
    --min-consecutive 2
```

Что смотреть: `test_recall` (доля пойманных «зере») и `test_fa_per_hour`
(сколько раз в час ассистент проснётся сам). Отчёт — `eval_report.md`.

Проверка контракта и всего конвейера без реальных данных:

```bash
python -m tools.wake_word.self_test          # OK, ~3 с
python -m tools.wake_word.self_test --keep   # оставить артефакты для разбора
```

`self_test` прогоняет девять шагов и проверяет по существу:

| Шаг | Что проверяется |
|---|---|
| 2 | математика frontend: базис ДПФ (Conv1d) против независимого numpy-FFT |
| 3 | пер-оконная нормализация: mean ≈ 0, std ≈ 1 |
| 4 | разбиение: изоляция групп **и** покрытие train/val/test (позитивы + негативы) |
| 5 | неполное разбиение падает с понятным `SplitError`, а не даёт нулевые метрики |
| 6 | датасет: форма окон `(16000,)`, значения в [-1, 1], оба класса |
| 8 | контракт ONNX: имена, формы, opset 17, отсутствие DFT/STFT, паритет torch↔onnxruntime (< 1e-3), `score` ⊂ [0, 1] |
| 9 | манифест: ровно контрактные ключи, отчёт оценки, непустые метрики test |

Всё пишется во временный каталог (и корпус, и модель) — реальные
`data/wakeword` и `ZERE.Voice/WakeWord/models` не трогаются.

Хотите проверить рантайм до того, как собраны реальные данные:
`python -m tools.wake_word.self_test --keep`, затем возьмите `wake_zere.onnx`
и `wake_zere.json` из напечатанного каталога (модель обучена на синтетике —
для проверки загрузки и интеграции, не для качества).

## 8. Если метрики плохие

**`recall` низкий (пропускает слово)**

1. Добавьте живых записей: `record_positives.py --count 100` — и обязательно
   с новыми условиями (дальше, тише, быстрее).
2. Проверьте позиционирование: слово в файлах должно звучать в конце окна
   ([0.80, 1.00] с). Слишком раннее слово детектор не поймает по построению.
3. Убедитесь, что синтез не «съел» слово: послушайте файлы из
   `positive_synth/`.
4. Снизьте порог в манифесте (но тогда вырастет FA/час) или увеличьте
   `min_consecutive`/`cooldown_ms`.

**`FA/час` высокий (просыпается сам)**

1. Добавьте негативы из СВОЕЙ комнаты и с ТВ/YouTube — это самый быстрый
   эффект: `build_negatives.py --from-dir <папка>`.
2. Добавьте похожие слова: `build_negatives.py --hard --hard-count 40`.
3. Обучите с `--neg-per-pos 3` (больше фона в эпохе).
4. Поднимите порог: взять значение из таблицы `eval_report.md`, где FA/час
   приемлем, а recall ещё ≥ 0.97, и вписать в манифест.

**Метрики хорошие на `val`, плохие на `test`** — почти всегда утечка или
мало данных. Проверьте, что группы записей не разъехались между разбиениями
(`self_test` проверяет именно это), и увеличьте набор.

**Обучение «не учится»** — проверьте, что в `data/wakeword/` реально есть и
позитивы, и негативы (`build_negatives.py` без аргументов печатает сводку
корпуса).

## 10. Заметки по Windows

* Все пути — через `pathlib`, POSIX-вызовов нет.
* Запуск: `python -m tools.wake_word.<скрипт>` из корня репозитория.
* Запись — только в Windows (в WSL микрофон обычно не проброшен).
* `--device cuda` требует CUDA-сборку torch; без неё обучение честно
  предупредит и пойдёт на CPU.
* Ресемплинг и чтение WAV сделаны на numpy/stdlib `wave`, без POSIX-утилит.
